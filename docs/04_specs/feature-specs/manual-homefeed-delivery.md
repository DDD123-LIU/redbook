## 已确认的行为契约

- 用户手动提交一次独立的“本流程推荐请求”。候选仅来自刷新后的小红书首页推荐流，不主动关键词搜索。
- 不设定时推送，不等待北京时间12:00；用户未发指令时不自动产生推荐请求。
- 每个独立请求目标10篇。同日可以发起多次请求，不设每日总量上限。
- 计时从请求提交开始，到逐条成功回执为止。首页刷新、候选采集、分析、去重和投递都计时。
- 后续无总运行时限，不设5分钟/300秒或替代固定总窗。3分钟仅为非强制效率期望，超过不构成停止、失败或验收不通过。单次接口调用仍有有限超时，暂时故障有限重试。用户停止、持续失败或必要条件缺失时保存检查点并报告实际数和缺口；不凑数，少于10篇不称数量达成。
- 历史索引的一次性初始化单独计时。不得把当天候选预先分析并排除在请求用时之外。
- 初始化就绪与其实际数据覆盖须单独披露；不得在本次请求启动后临时把必要准备耗时排除。有效历史采集/分析可按内容指纹和适用性复用，这不等于提前准备本次候选。
- 去重依据仅为实际取得的收藏记录和本系统投递台账。覆盖不全时说明缺口，不因此全局阻断。
- 已知重复项跳过。投递结果为 unknown 时，先核实再决定后续操作，不直接重发。
- 2026-10-20去重澄清（Codex）：仅帖子ID相同才跳过；ID不同默认不同，不比较正文、图片或语义。内容hash只用于缓存完整性，不用于跨ID去重。无正文缓存不阻塞ID判断；偏好和质量筛选独立执行。已发送记录中的同ID跳过；本系统发送unknown先核实，不盲发。
- 当前请求内也按ID跳过重复；ID无法可靠取得时记录该候选身份未核实，不根据标题猜ID。收藏范围沿用已确认范围；当前最新10篇仅属有界测试，不自动转为全项目永久范围。
- 未覆盖历史引起的“是否重复未知”与某次已发请求的“送达回执unknown”分开记录；前者按已确认范围披露，不能借此绕过后者的核实要求。
- 逐条成功回执用于判断投递完成。客户端实际可见状态未经核验时，必须单独标记未核验。
- 不删除既有投递、反馈和来源证据。
- 沿用既有本人飞书B样式：每篇独立一条，保留标题、作者、原正文、有序图片和原文入口，不为速度静默改摘要或省图。性能目标不改变原有质量门槛。

## 验收场景草案

- 单次请求取得并成功投递10篇：核对开始/结束时间、逐篇成功回执及总数；另行记录客户端可见状态是否核验。
- 分别记录首篇及第20篇成功时间、各阶段实际耗时、候选/分析/去重淘汰/成功投递数量、缓存复用和覆盖范围。不以总耗时判失败；数量、质量和回执分别验收。
- 超过3分钟或旧5分钟且不足10篇：不因总耗时停止或判失败，可继续同一请求；用户停止或持续失败/必要条件缺失时保存进度并报告，不凑数。
- 刷新或任一中间步骤耗时：全部计入请求时长，不以预先处理当天候选缩短表面计时。
- 去重资料覆盖不全：披露已取得的数据范围和未知范围；不得声称全局无重复。
- 已知重复：跳过并留记录。发送状态unknown：先核实，不直接重发。
- 不同ID即使正文/图片相同，也按不同帖子进入偏好及质量筛选；不运行内容去重。相同ID更换链接参数、标题或正文，仍不新增一篇。
- 同日提交第二个独立请求：仍以10篇为目标，不受每日总量限制。
- “继续上次”只恢复原批未完成项；“开始新一轮”创建目标10的新批。跨日旧批结束并保留记录；刷新首页后开新批，复用有效成果并防重成功ID。实现由TASK-013承接，技术集成由TASK-015验证。
- 明确“试跑3条”目标3；探索原3条与本流程批次的关系未定，不据此改探索或F08。
- 用户停止后不启动新步骤；核实已发请求并归账，unknown保留待查，已成功结果不撤回。通过证据须覆盖已成功、明确失败和unknown三类。
