同一内容更正后只计当前有效评价，不重复计数；保留更正依据。
消息根本未送达时系统无法知晓，没有回执不能视为已确认反馈。
验收：重复事件、更正、保存失败、跨批次歧义测试可核对，指标可从记录复算。

### F07 故障恢复
短暂故障有限重试，单次调用有有限超时，不再受全流程总时限约束；持续失败保存检查点并报告已知原因、进度、缺口及必要操作，不明原因如实说明。不以取消总时限支持无限重试。
登录过期或验证码不盲目重试；筛选失败不把未筛候选直接推给用户。
已知失败项可按有限重试与恢复规则处理；结果 unknown 时先核实。已有受限的平台回执查询证据，正式产品集成及长期可靠性仍未验证。飞书故障保留进度并报告。跨日按F03/F04确认：旧批结束并留记录，刷新首页后新建批；具体状态实现待TASK-013/015。用户停止后不启动新步骤；核实已发请求并归账，unknown保留待查，已成功结果不撤回。该行为的产品实现仍待TASK-013/015验证；停止不代表底层请求已即时取消，也不盲重发。不再按旧总截止时间判回执不合格。
验收：不得以“超时”直接认定未送达并盲目重发。次数、间隔及无法核实状态的处置留待 Spec。

### F08 品味一致率与长期 review
2026-10-21 Codex：TASK-005用户已逐项确认看过无赞踩计E并单记S；约定期间全部成功唯一推荐入N，失败单列，投递unknown先核实且未解不通过；最后确认投递后48小时截止，迟到/更正形成新修订且保留原报告与原结论。此覆盖下方相应“待确认”历史描述。N=L+D+E，阈值以原始整数比较；总量/充分性留试用。完整行为以quality-feedback.md v0.2为准，非真实质量通过。
用户进一步明确：不能只看一致率，还必须分析缺少评价状态的原因，检查系统是否稳定。此处“异常”指一批中无法取得明确赞/踩状态，包括用户未操作或系统未读取/保存成功，建议指标名为评价缺失率。不能把全部缺失归为用户未评价，也不能把全部缺失当系统失败。
review 必须检查投递状态、反馈是否到达、解析及关联是否成功、保存结果与回执结果。能确认的链路故障作为系统 bad case 修复；没有足够证据的原因标未知，不假定用户没点。用户未操作不代表不喜欢，不应自动制造评价或反复催评来改善数字。
分别展示评价缺失率、有效评价一致率及有证据的链路故障情况。系统可靠性问题与偏好问题分别处理：先补查/修复反馈记录，避免将数据丢失造成的比例偏差误当品味变化。缺失率不通过时，该批不能用于宣布品味验收通过；系统故障或原因未知需继续排查，不能只剔除缺失样本后宣称成功。
样本有效性与一致性采用双门槛（用户新增）：设某批样本总数 N、异常数 E、点赞数 L、点踩数 D。异常率 E/N 必须严格小于 5%，该批样本才可用于判定一致性通过；有效评价一致率 L/(L+D) 必须大于等于 95%。任一门槛未满足则该批不通过，不能只报告有效评价的一致率。
用户示例：100 条中异常 1、赞 95、踩 4；异常率为 1%，有效评价一致率为 95/99≈95.96%，双门槛均通过。异常率恰为 5% 不通过，一致率恰为 95% 通过。无样本或无有效赞踩时无法判定通过，不把除零显示为 0% 或 100%。
“异常”已按用户定义为统计样本中无法取得明确赞/踩的评价缺失，包括未操作或系统读不到；采集/展示故障同时作为独立链路事件记录，是否进入推荐样本分母须在 Spec 明确。“看过”不计一致率，其单独无赞踩时如何计缺失仍待确认。未评价不计赞踩分母，但必须计入缺失排查，不能剔除后宣称样本充分。样本分类与 N/E/L/D 关系、观察截止时间及统计批次需明确，每次投递 3 条不自动等同验收统计批次。
定义：每类一致率 = 该类有效赞数 /（该类有效赞数 + 该类有效踩数）。
未评价和看过不计入；看过另记重复反馈。没有赞踩则暂无数据，不能判达标。
展示分子分母及覆盖率。覆盖率展示应区分“收到任何反馈”和“收到赞踩”；看过不应提高有效赞踩覆盖率。
初测：从开始测试累计，两类各自至少 95%；每批 3 条，总量试用时确定。3 条全赞不能自动替代约定测试完成。
正式期：保留历史累计、按策略版本统计，同时 review 近期表现，避免历史高分遮蔽下降。
低于目标：查 bad case，区分兴趣变化、候选分布、采集/筛选/反馈问题；调整并记录版本。
恢复：只评估新规则产生的新推荐，两类各自至少 95%；最迟第 2 个调整版本仍失败即本轮质量验收失败，报告原因和后续选项。不得清除旧点踩或给旧候选换版本号制造达标。
未授权自动停推；是否暂停由后续明确指令或约定决定。
验收：指标可复算，版本和反馈可追踪，review 有案例、归因、改动与复查结果，不凭无反馈宣布稳定。
